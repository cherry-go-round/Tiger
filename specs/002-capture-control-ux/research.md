# 조사: Capture Control UX

## 결정: 원시 데이터는 DB blob이 아닌 내부 파일 bundle로 유지

**근거**: 영상·CSV 스트림은 이미 검증 가능한 불변 bundle이다. 기존 root를 앱 전용 내부 파일 저장소로 옮기면 일반 파일 관리자 삭제를 막으면서 finalize·manifest 검증·export·multipart 업로드 계약을 유지할 수 있다. Room은 목록·상세 색인에 적합하다.

**검토한 대안**:

- 원시 영상·CSV를 Room에 저장: 대용량 binary 저장은 기존 bundle 계약을 개선하지 못하고 export·upload를 불필요하게 복잡하게 만든다.
- 앱 전용 외부 저장소 유지: 파일 삭제에 따른 불일치를 해소하지 못한다.

## 결정: 관리 root 검증으로 legacy 외부 bundle 제외

**근거**: 기존 완료 행은 Room에 남겨도 된다. repository는 canonical bundle path가 내부 completed root 하위일 때만 Session을 노출하고 직접 업로드도 같은 조건으로 막는다. 복사·삭제·DB migration 없이 이전 데이터 제외 요구를 충족한다.

**검토한 대안**:

- legacy bundle을 내부 저장소로 복사: 합의된 범위 밖이다.
- legacy 행이나 파일 삭제: 사용자가 파괴적 정리를 승인하지 않았다.
- 문자열 prefix 필터: 정규화되지 않은 경로에서 안전하지 않다.

## 결정: 업로드 상태 화면이 취소 가능한 전송 작업 소유 (2026-09-18 아래 결정으로 대체)

**근거**: 현재 업로드 서비스는 종료 상태만 제공한다. 화면이 소유한 coroutine 작업에서 취소를 실제 HTTP 요청까지 전달하면, 확인된 이탈 또는 백그라운드 전환 시 `UPLOADING`을 `FAILED`로 남길 수 있다. 서버 진행률 API는 없으므로 기존 HTTP 응답이 올 때까지 비결정적 진행 표시를 쓴다.

**검토한 대안**:

- 사용자 시작 데이터 전송 작업 또는 전면 서비스로 백그라운드 계속 전송: 백그라운드 전환 시 취소한다는 UX와 맞지 않는다.
- Session Detail에 전송 수명주기 결합: Detail은 시작만 담당하고, 진행·취소는 업로드 상태 화면이 담당해야 한다.

## 결정: 전송 진행을 Session Detail로 옮기고 업로드 상태 화면을 없앤다 (2026-09-18 갱신, S15P21A206-34)

**근거**: 위 결정에서 대안으로 접어 두었던 "Session Detail에 전송 수명주기 결합"을 채택한다. 마감과
전송은 성격이 다르다. 마감은 로컬 I/O라 짧고, 그동안 Session이 아직 저장되지 않아 벗어날 곳이
없다. 전송은 네트워크에 매여 수백 MB면 분 단위가 될 수 있고, 그 시점에는 Session이 이미 저장되어
존재한다. 존재하는 것에 무슨 일이 일어나는지는 그것의 화면에서 보여 주면 된다.

취소를 화면이 소유해야 한다는 전제도 함께 내려놓는다. 전용 화면에서는 "나간다"가 곧 "그만둔다"로
읽혔지만, Detail은 둘러보는 화면이라 같은 동작을 중단 의사로 읽으면 사고가 된다. 사용자가 전송을
중간에 끊는 수단을 두지 않는 대신, 실패하면 Detail에 사유와 재전송을 함께 두어 막히지 않게 한다.
백그라운드 전환 시 취소는 유지하되 판정 기준을 화면이 아니라 전송 진행 여부로 바꾼다.

마감 구간의 진행 표시는 작업 공간을 덮는 판으로 옮긴다. 그 구간에는 어떤 제어도 받지 않는데 진행
표시를 제어와 같은 줄에 두면 누를 수 있는 것처럼 보였다.

**검토한 대안**:

- 마감과 전송을 한 판에서 이어 보여 주기: 전송이 길어지는 동안 사용자를 덮인 화면에 가둔다. 그
  시점에는 카메라 자원도 이미 놓은 뒤라 판 뒤에 멈춘 화면만 남는다.
- 업로드 상태 화면 유지: 성공하면 스스로 닫히도록 바꾼 뒤로는 사라지려고 존재하는 화면이 됐다.

## 결정: 조회 흐름의 화면 전환을 Navigation Compose로 옮긴다 (2026-09-17 갱신, S15P21A206-40)

**근거**: `androidx.navigation:navigation-compose`가 백스택을 소유하고, 각 화면의 이탈은
`popBackStack()`으로 통일한다. Task 이름·Session 식별자는 type-safe route로 전달한다. 수집 작업
공간은 목적지가 아니라 NavHost 위의 모달로 두고 boolean 상태로 관리한다.

**이전 결정과 뒤집는 이유**: 원래 결정은 "새 navigation 의존성 없이 명시적 화면 상태 사용"이었다.
근거는 "단일 Compose root이고 sealed 목적지와 콜백이 의존성 추가 없이 결정론적 뒤로 가기를
제공한다"였고, 대안인 Navigation Compose는 "의존성 추가는 별도 승인 대상이므로 보류"했다.

그 근거는 구현에서 지켜지지 않았다. hoisting한 `destination` 단일 상태에는 백스택이 없어,
`BackHandler`를 둔 수집 작업 공간과 업로드 상태를 뺀 모든 화면에서 시스템 뒤로 가기가 Compose에
잡히지 않고 Activity 기본 동작으로 넘어가 앱이 종료됐다. 돌아갈 곳도 하드코딩돼 있어 Session
상세의 이탈은 진입 경로와 무관하게 `TaskSessions(summary?.taskName)`로 고정됐고, summary가 없으면
빈 Task 이름으로 이동했다. `destination`이 저장 상태에 실리지 않아 프로세스 재생성 시 홈으로
돌아가는 문제도 남았다. 화면 수가 더 늘어나는 상황에서 백스택을 직접 구현하는 비용이 의존성
추가 비용을 넘어섰다. 의존성 추가는 2026-09-17 사용자 승인을 받았다.

**검토한 대안**:

- `destination` 위에 직접 백스택 리스트를 얹기: pop·중복 진입·저장 상태 복원·predictive back을 모두
  직접 구현해야 하고, 그것이 곧 navigation 라이브러리를 다시 만드는 일이다.
- route 문자열 직접 조립: Task 이름은 사용자 자유 입력이라 `/`·공백이 경로를 깨뜨린다. type-safe
  route가 인자 직렬화를 담당한다.

## 결정: 전체 화면 동영상은 목적지로 유지한다 (2026-09-17, S15P21A206-40)

**근거**: S15P21A206-38이 Media3로 이관한 결과, 전체 화면 재생은 상세 화면 플레이어의 확장이
아니라 검은 배경·가로 고정·독자 컨트롤을 가진 별도 화면으로 남았다. 계약의 이탈 동작도 "Session
Detail 복귀"로 정의돼 있어 백스택 pop과 정확히 맞는다. 재생 위치는 두 화면이 공유하는
`SharedVideoPlayer`가 유지하므로 목적지를 나눠도 재생이 끊기지 않는다.

**검토한 대안**:

- 상세 화면 안의 전체 화면 상태로 접기: 방향 정책과 컨트롤 구성이 달라 상세 화면에 두 벌의 표시
  규칙이 생기고, 뒤로 가기도 pop이 아닌 별도 가드가 된다.

## 결정: 라이브 프리뷰 준비와 녹화 시작 분리

**근거**: 현재 runtime은 카메라·ARCore·writer를 함께 시작하고 화면에 렌더링된 프리뷰가 없다. 작업 공간은 권한·AR preflight 이후 프리뷰 전용 camera surface를 준비하고, 유효한 task/object와 첫 재생 이후에만 원시 녹화를 시작해야 한다. 프리뷰 실패 시 재생을 막고 다음 행동을 안내한다. (구현) 프리뷰 쪽은 카메라 권한과 Surface만 확인하고 연다. ARCore 설치 확인과 카메라 시각 `REALTIME` 확인은 첫 재생(Session 시작)에서 한다.

**검토한 대안**:

- 녹화 surface를 프리뷰로 간주: Session 생성과 원시 녹화보다 먼저 프리뷰를 보여야 하는 요구와 맞지 않는다.
- 프리뷰 생략: 핵심 사용자 흐름을 충족하지 못한다.

## 결정: 로컬 벽시계 수집 시작 시각 추가

**근거**: 기존 monotonic timestamp로는 길이는 계산할 수 있지만 앱 재시작 뒤 표시할 날짜·시각은 만들 수 없다. Room migration으로 새 Session에만 로컬 벽시계 시작 시각을 기록하며, 원시 bundle과 서버 multipart 계약은 바꾸지 않는다.

**검토한 대안**:

- 길이만 표시: Session Detail의 수집 시각 요구와 맞지 않는다.
- monotonic time에서 벽시계 time 추론: 기기 재시작 뒤 안정적이지 않고 달력 시각을 보장하지 못한다.
