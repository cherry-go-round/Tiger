# 보조 명세: Mobile Episode Transfer

**상위 기능 ID**: `001-episode-recorder`
**작성일**: 2026-09-01
**상태**: 초안
**입력**: 스마트폰 기반 Egocentric Human Demonstration 수집 앱 MVP의 episode 업로드에 필요한 모바일 관점 통신 계약을 정의한다.

## 목표

수집자는 로컬에 완결된 사람 시연 episode 하나를 원격 서비스로 안전하게 전송하고, 성공 여부를 확인하며 실패 시 원본을 보존한 채 수동으로 재전송할 수 있다. 이 명세는 앱과 서버 사이의 통신 계약만 정의하며 서버의 언어, 데이터베이스, 배포, 저장소 구현 및 후처리 구현은 정의하지 않는다.

`task`는 조작 과업 카테고리(예: `pick_cup`)이고, `episode`는 한 번의 연속된 시연 녹화 단위다.

## Clarifications

### Session 2026-09-02

- Q: 앱은 서버 업로드 요청을 어떤 방식으로 인증해야 하나요? → A: 폐쇄망 MVP에서는 인증 없이 업로드한다.
- Q: 서버가 업로드 요청을 성공으로 처리했음을 앱에 어떤 응답으로 알려줘야 하나요? → A: 새 수신은 `201 Created`, 동일 Idempotency-Key의 중복 수신은 `200 OK`로 응답하고, 두 응답 모두 JSON에 `episode_id`와 `created` 또는 `duplicate` 결과를 포함한다.
- Q: 서버 오류 응답을 앱의 `FAILED`와 `RETRY_REQUIRED` 중 어느 상태로 분류해야 하나요? → A: `RETRY_REQUIRED` 상태는 사용하지 않는다. receipt 성공 조건을 만족하지 않는 모든 HTTP·transport 결과는 `FAILED`로 기록하고, 수집자는 필요할 때 수동 재전송한다. `401`·`403`은 인증 없는 MVP에서 사용하지 않는다.
- Q: 앱은 업로드할 서버 주소를 어디에서 받아야 하나요? → A: 앱 빌드 시 서버 base URL을 설정한다.
- Q: 인증 없는 폐쇄망 MVP에서도 앱과 서버 사이의 업로드 연결은 HTTPS로 보호해야 하나요? → A: 신뢰 가능한 인증서의 HTTPS만 허용한다.
- Q: 단일 multipart 업로드가 중간에 끊기면 앱은 다음 시도에서 어떻게 전송해야 하나요? → A: 재전송마다 6개 파일 bundle 전체를 다시 보낸다.

## 사용자 시나리오 및 테스트 *(필수)*

### 사용자 스토리 1 - 완결 episode 수동 업로드 (우선순위: P1)

수집자는 로컬에 저장된 completed episode를 선택해 한 번의 업로드 요청으로 원격 서비스에 전달하고 그 결과를 확인한다.

**우선순위 근거**: 원본 시연을 잃지 않고 후속 검증·처리에 전달하는 것이 이 기능의 핵심 가치다.

**독립 테스트**: 완결된 episode 한 건을 업로드해 서버가 수신 성공을 응답하면 앱이 완료 상태를 표시하고 로컬 원본을 유지하는지 확인한다.

**인수 시나리오**:

1. **Given** 전송 가능한 completed episode가 있고, **When** 수집자가 업로드를 시작하면, **Then** 앱은 해당 episode의 metadata와 원본 파일을 하나의 multipart 요청으로 전송하고 진행 상태를 표시한다.
2. **Given** 원격 서비스가 새 수신 `201 Created` 또는 중복 수신 `200 OK`와 `episode_id`·결과 JSON을 응답했고, **When** 앱이 응답을 처리하면, **Then** 앱은 episode를 업로드 완료로 표시하고 로컬 episode 폴더를 유지한다.
3. **Given** 녹화 중·취소됨·오류 상태이거나 필수 파일이 불완전한 episode가 있고, **When** 수집자가 업로드를 시도하면, **Then** 앱은 네트워크 요청을 만들지 않고 이유를 알린다.

---

### 사용자 스토리 2 - 실패한 업로드 수동 재전송 (우선순위: P2)

수집자는 전송 실패 후에도 원본 episode를 잃지 않고 같은 episode를 수동으로 다시 전송한다.

**우선순위 근거**: 수집 환경의 네트워크 불안정은 원본 데이터의 손실이나 중복 수집으로 이어져서는 안 된다.

**독립 테스트**: 전송 도중 연결을 끊거나 서버가 실패를 응답하게 한 뒤 같은 episode를 다시 전송하여, 원본이 보존되고 최종 상태가 갱신되는지 확인한다.

**인수 시나리오**:

1. **Given** 업로드가 실패한 completed episode가 있고, **When** 수집자가 재전송을 요청하면, **Then** 앱은 같은 episode 식별자로 새 요청을 보내고 로컬 파일을 수정하거나 삭제하지 않는다.
2. **Given** 이전 요청의 결과를 앱이 받지 못한 episode가 있고, **When** 수집자가 재전송하면, **Then** 서버는 동일 episode가 중복 수집되지 않도록 요청을 식별하고 앱은 그 결과를 표시한다.

---

### 사용자 스토리 3 - 전송 상태 확인 (우선순위: P2)

수집자는 episode 목록에서 아직 업로드하지 않은 항목, 업로드 중인 항목, 완료된 항목 및 재전송이 필요한 항목을 구분한다.

**우선순위 근거**: 수집자는 어느 시연이 원격 후속 처리에 전달됐는지를 현장에서 판단해야 한다.

**독립 테스트**: 전송 전·진행 중·완료·실패 상태의 episode를 준비해 목록에서 상태와 마지막 결과를 구분해 표시하는지 확인한다.

**인수 시나리오**:

1. **Given** 서로 다른 전송 상태의 episode가 있고, **When** 수집자가 목록을 열면, **Then** 각 항목의 전송 상태, 마지막 시도 시각 및 실패 요약을 확인할 수 있다.

### 예외 상황

- 네트워크가 없거나 하나의 업로드 요청 도중 연결이 끊기는 경우, 앱은 실패로 표시하고 원본을 유지한다.
- 중단된 업로드를 재전송하는 경우, 앱은 업로드 세션 또는 파일 오프셋을 사용하지 않고 6개 파일 bundle 전체를 새 요청으로 전송한다.
- 서버가 입력 거부 또는 일시 오류를 응답하는 경우, 앱은 서로 구분되는 이유를 표시한다.
- 연결 오류, 모든 HTTP 오류, 계약에 맞지 않는 success receipt는 `FAILED`로 기록하고 원본을 유지한다. 수집자는 마지막 시도의 HTTP status·server error code·실패 요약을 확인한 뒤 필요할 때 수동 재전송한다. 인증 없는 MVP 서버는 `401`·`403`을 응답해서는 안 된다.
- 업로드 시작 전 또는 도중 사용자가 앱을 종료하는 경우, 진행 중 요청은 완료로 표시되지 않으며 원본은 유지된다.
- 로컬 파일의 크기 또는 SHA-256이 metadata의 기록과 일치하지 않는 경우, 앱은 업로드를 시작하지 않는다.
- 신뢰할 수 없는 인증서 또는 HTTPS가 아닌 서버 주소인 경우, 앱은 업로드를 시작하지 않는다.

## 요구사항 *(필수)*

### 기능 요구사항

- **FR-001**: 시스템은 completed 상태의 episode만 업로드 대상으로 허용해야 하며, 녹화 중·취소됨·오류 episode는 업로드해서는 안 된다.
- **FR-002**: 시스템은 업로드 전에 episode의 metadata, 필수 원본 파일, 파일별 크기 및 SHA-256을 검증해야 하며, 검증에 실패하면 요청을 시작해서는 안 된다.
- **FR-003**: 시스템은 episode 하나를 업로드 단위로 사용하고, 사용자가 명시적으로 시작한 경우에만 업로드해야 한다. 자동 업로드, 백그라운드 업로드 및 재시도 큐는 MVP 범위 밖이다.
- **FR-004**: 시스템은 `POST /episodes`에 `multipart/form-data` 한 요청으로 metadata JSON, MP4 영상, frame timestamp CSV, accelerometer CSV, gyroscope CSV 및 rotation vector CSV를 전송해야 한다. 파트 이름은 각각 `metadata`, `video`, `frame_timestamps`, `accelerometer`, `gyroscope`, `rotation_vector`를 사용해야 한다.
- **FR-005**: 시스템은 HTTP header에 `Idempotency-Key`처럼 작은 제어 정보만 넣어야 하며, episode metadata 전체를 header에 넣어서는 안 된다. 폐쇄망 MVP의 업로드 요청에는 인증 자격 증명을 넣어서는 안 된다.
- **FR-006**: 시스템은 동일 episode의 재전송마다 동일한 `episode_id`를 `Idempotency-Key`로 전달해야 하며, 서버가 이미 수신한 동일 episode를 중복 생성하지 않도록 하는 응답을 처리해야 한다.
- **FR-007**: 시스템은 업로드 성공 전에는 로컬 episode 폴더 또는 원본 파일을 삭제하거나 변경해서는 안 되며, 성공 후에도 MVP에서는 자동 삭제해서는 안 된다.
- **FR-008**: 시스템은 `LOCAL_ONLY`, `UPLOADING`, `UPLOADED`, `FAILED` 상태와 마지막 시도 시각·HTTP status(있는 경우)·server error code(있는 경우)·실패 요약을 episode별로 로컬에 보존하고 표시해야 한다. receipt 성공 조건을 만족하지 않는 모든 HTTP·transport 결과는 `FAILED`로 기록해야 한다. 인증 없는 MVP 서버는 `401`·`403`을 응답해서는 안 된다.
- **FR-009**: 시스템은 요청 형식 또는 데이터 검증 거부와 재시도 가능한 일시 오류를 수집자가 구분할 수 있게 표시해야 한다.
- **FR-010**: 시스템은 서버가 새 수신에 대해 `201 Created`, 동일 `Idempotency-Key`의 중복 수신에 대해 `200 OK`를 응답하고, 두 경우 모두 JSON의 `episode_id`와 결과값 `created` 또는 `duplicate`를 제공한 경우에만 업로드 완료로 상태를 변경해야 한다. 후처리 상태는 업로드 상태와 분리하며, MVP 앱은 후처리 진행·결과를 조회하지 않는다.
- **FR-011**: 시스템은 앱 빌드 시 주입된 서버 base URL과 통신해야 하며, 수집자가 앱 화면에서 주소를 입력하거나 수정해서는 안 된다. 실제 base URL 값은 저장소와 명세에 기록해서는 안 된다.
- **FR-012**: 시스템은 신뢰 가능한 인증서로 보호되는 HTTPS 서버 base URL에만 업로드 요청을 보내야 하며, 평문 HTTP 또는 인증서 검증 우회 연결을 허용해서는 안 된다.
- **FR-013**: 시스템은 서버로부터 요청 수신 성공의 판정 기준, 오류 분류 및 중복 요청 처리 결과를 통신 계약으로 제공받아야 한다. 서버의 내부 데이터 모델과 저장 방식은 정의하지 않는다.
- **FR-014**: 시스템은 `video.mp4`, `frame_timestamps.csv`, `accelerometer.csv`, `gyroscope.csv`, `rotation_vector.csv`, `metadata.json`의 여섯 파일을 하나의 episode 원본 bundle로 전송해야 한다.
- **FR-015**: 시스템은 `FAILED` 상태의 업로드를 수집자가 명시적으로 재전송할 때, 같은 `episode_id`와 `Idempotency-Key`를 사용해 여섯 파일 bundle 전체를 새 `POST /episodes` 요청으로 전송해야 한다. 업로드 재개 세션 또는 파일 오프셋 전송은 지원해서는 안 된다.

### 범위 외

- 서버의 데이터베이스, 언어·프레임워크, 배포 구조, 작업 큐, 파일 저장소 또는 GPU 처리 환경의 구체적 설계.
- 서버 원본 보관 위치와 storage backend/key의 실제 값 또는 public URL 정책.
- 원본 수집 데이터의 영구 보관, processing run·processing file 생성, ORB-SLAM3 등의 후처리 구현.
- 업로드 성공 뒤 checksum 재검증 및 자동 로컬 삭제.
- background upload, 자동 재시도 큐, 실시간 스트리밍.
- 중단 지점부터 재개하는 업로드 세션 또는 파일 오프셋 전송.
- 촬영 데이터 미리보기와 episode 관리 화면의 상세 설계.

### 핵심 엔터티

- **업로드 대상 episode**: task code 아래에 저장된, 원본 파일과 metadata가 완결된 한 번의 연속 시연 녹화.
- **업로드 요청**: 하나의 episode를 원격 서비스에 전달하는 단일 multipart 요청. metadata와 원본 파일, 중복 방지 제어 정보를 가진다.
- **업로드 상태**: 로컬 전송 전·전송 중·완료·실패·재전송 필요를 나타내는 episode별 상태와 마지막 시도 결과.
- **원격 수신 결과**: 새 수신 `201 Created` 또는 중복 수신 `200 OK`의 JSON `episode_id`와 `created`/`duplicate` 결과, 또는 거부·재시도 필요를 나타내는 응답.

## 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: 수집자는 completed episode 하나를 선택해 한 번의 수동 업로드 요청을 시작하고, 요청 시작 후 5초 이내에 전송 상태를 확인할 수 있다.
- **SC-002**: 서버가 수신 성공을 응답한 episode의 100%는 앱에서 업로드 완료로 표시되고 원본 로컬 파일은 유지된다.
- **SC-003**: 연결 끊김 또는 서버 실패로 완료되지 않은 업로드의 100%는 원본 episode를 유지하고 수집자가 수동 재전송할 수 있다.
- **SC-004**: 로컬 완결성 검증에 실패한 episode는 원격 요청을 만들지 않으며, 수집자는 실패 이유를 확인할 수 있다.
- **SC-005**: 같은 episode를 재전송했을 때 서버가 중복으로 만들지 않았음을 나타내는 수신 결과를 앱이 표시할 수 있다.

## 가정

- 서버 base URL은 신뢰 가능한 인증서의 HTTPS 주소로 빌드 시 앱에 주입되며, 수집자는 앱 화면에서 이를 변경하지 않는다. 서버는 `POST /episodes` multipart 요청을 수신하고, 새 수신에는 `201 Created`, 중복 수신에는 `200 OK`와 JSON `episode_id`·`created`/`duplicate` 결과를 제공한다.
- MVP 서버는 폐쇄망에서 접근하며 인증을 요구하지 않는다. 공개망 또는 다중 사용자 환경의 인증 방식은 이 MVP 범위 밖이다.
- 서버는 수신 뒤 원본과 후처리 결과를 분리해 보관할 수 있으나, 이 기능은 그 내부 구현을 전제하거나 제어하지 않는다.
- `task`는 조작 과업 카테고리이며, task 폴더명과 metadata의 `task` 값은 동일하다.
